# Project Z coordination protocol

Status: source-grounded coordination protocol. This file does not itself lock the architecture; require the actual product-lock and execution-pack manifests before launch. No execution phase has launched.

## Roles and records

- PRD/coordinator: owns the one common product lock, source/ownership/contracts, integration queue, three-slot schedule, truthful programme status, and independent qualification coordination.
- Prompt-engineering chat: owns one exact reusable blueprint and six fully assembled phase prompts. It cannot change locked product predicates or invent source provenance.
- Six phase chats: each owns only its locked prefix and versioned leaf integrations on its own branch/worktree and dedicated Computer. Each receives the complete common PRD and applicable source/prompt/handoff context.
- Independent validators: inspect actual source/runtime/receipt evidence under the same model restriction. Mathematical independence, protected custody, and authority come from governed specifications/checkers, not from a different chat.

Engineering controller files are not product admission/effect/financial records.

## Model and authority policy

Every model role is exactly `gpt-6.1-sol`, reasoning `max`. No aliases, automatic routing, cheaper workers, generated droids, default light subagents, or alternate-model review. Pin orchestrator, worker and validator flags as well as runtime settings. Inspect actual receipts; a requested flag alone is not proof of the model that ran.

Native mission mode and ordinary CLI sessions are distinct. The installed CLI offers native mission mode with explicit worker/validator flags and requires high autonomy; native proposals are auto-approved. That facility does not authorize outward actions excluded by the mission. Never use `--skip-permissions-unsafe` to bypass a missing approval. If a native facility is unavailable, retain that exact failure and name any ordinary/local fallback honestly.

Task-owned source changes, reversible disposable verification, local commits and context delivery to this programme's requested chats are authorized. No unsolicited messages to unrelated workstreams. No push/PR/merge, production deployment, protected activation, grants/signers, customer/counterparty contact, funds, or real economic commitments.

Computer creation uses the six already staged desktop proposals. The proposals are not API creation receipts and cannot be bypassed with a shell/API provisioning path. Observe actually created Computers only; do not infer creation from staging.

## Layered immutable lock

Avoid self-referential hashes:
1. Retain supplied sources and source-reading/availability audit.
2. Freeze one PRD, common contract schemas, profile/ownership register and source index.
3. Seal those product inputs in a content-hashed product-lock manifest.
4. Author and assemble each complete phase prompt against that product lock.
5. Seal blueprint, phase prompt bodies, full assembled seeds, roles, scheduling instructions and package/reconstruction inputs in a separate execution-pack manifest.
6. At each launch, add a separate immutable context snapshot with current actual source head, applicable received peer handoffs, queue position and existing external blockers. Never rewrite the product lock to hide later reality.

A source exception must remain explicit. Missing exact R1 bytes cannot be represented by a fabricated digest match.

## Required initial group and refill

Only after both common lock and complete execution pack exist:
- Submit launch requests for Z0, Z1 and Z2 as ONE concurrent launch group.
- Confirm three actual session-start/model/Computer receipts. Record partial launch failures or delayed starts; do not call launch requests active executions.
- Maintain at most three implementation slots. Research and certification are not substitute slots.
- On an ownership-stable scheduling handoff, perform only the check below and immediately request the next queued phase, strictly Z3, Z4, Z5.
- Run deeper source scrutiny, user testing, qualification, integration certification and statistical review separately. They must not delay an otherwise safe refill.
- Never mark unfinished internal work CODE_COMPLETE to free a slot. Preserve interrupted, incomplete, blocked and repair work explicitly. If the mandatory three active lanes cannot be maintained within real permissions/resources, record the exact shortfall.

No phase requires another Z mechanism to prove its first independent boundary. Use completed X/Y-compatible admitted inputs and the locked adapter seam. Consume newer peer artifacts only after actual delivery and applicability checking.

## Lightweight scheduling handoff, not certification

Verify:
1. Exact phase, product-lock, branch, source/base/tree and interface identities.
2. Changed-file and ownership manifest; shared edits are coordinated requests, not peer overwrites.
3. Durable finite verification dispositions and retained failures exist. No invented PASS or production claim.
4. Reconstructible source/patch/package references and actual applicable peer receipt hashes exist.
5. Outstanding integration requests, costs/meter gaps, authority blockers, S6 obligations/UNKNOWN and continuation ownership are explicit.
6. Next phase's context can be delivered on its own ready Computer without rewriting shared authority or blocked predecessor source.

This check may accept an honest engineering handoff while deeper qualification remains pending. It does not override missing required software or permit fabricated completion.

## Shared-write and integration queue

The coordinator owns the common schema/API/job registry, dependency locks, migrations, generated clients, build/global manifests and cross-owner integration. Phase workers own independent computation/checker leaves and task-local evidence.

A shared-change request carries an exact preimage-bound patch, symbol/type/version, callers, migration/compatibility impact, failure model and finite affected verification. The coordinator applies reviewed requests serially, returns actual commit/tree and receipt references, then the phase exercises its real installed owner path. A prepared patch is not a consumer-run receipt.

Do not choose migration numbers independently. Do not import peer dirty work, mutate active peer files or use a placeholder owner to declare integration.

## Context delivery and receipt

Every message/bundle declares sender role, intended phase, product-lock digest, source snapshot, content hashes, classification, and whether it is:
- REQUESTED,
- DELIVERED_WITH_RECEIPT,
- ACKNOWLEDGED_READ,
- NOT_DELIVERED,
- or DELIVERY_UNKNOWN.

The receiver verifies hashes before use and reports its actual checkout. Earlier prompts/handoffs are included when relevant in full, not a memory summary. At minimum every phase receives the complete locked PRD, its own full prompt, the common blueprint and contracts, the current source/ownership snapshot and all applicable engineering references/source exceptions.

No automatic cross-chat delivery is claimed until an actual session/API/CLI receipt exists. Versioned complete seeds are the honest fallback.
