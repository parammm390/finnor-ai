# Capability discovery: failure-first CLI contract

This is the permitted coordinator-owned discovery repair, not a dedicated Z0
execution, installed application proof, native-query repair or phase completion.
The product and execution locks are unchanged.

## Independent contract and primary proof owner

The real `planningCapabilitiesForVertical(createDefaultPluginRegistry(), ...)`
result owns the finite PE capability denominator and every planning metadata
field. The CLI contract invokes it directly through the installed TS loader,
independently of the generator or its proposed helper. It drives the real
generator and coverage auditor in a private source snapshot. It compares the
complete sets and metadata, not a copied list of today's six omissions.

Existing authenticated capability-discovery coverage owns conversational intake,
persisted Work identity and read-only replies. It does not exercise the frontend
manifest generator or independently check the coverage auditor's denominator.
No production export, flag or injection seam is added for this contract.

## Credible failures to exercise before product code

- Production/test registration differ, require credentials, or silently import
  workspace product code from the parent rather than the private snapshot.
- A generator loses any identity, reference, kind, proposability, health, risk,
  effect, recovery, observation, reversibility or authority metadata.
- Human decisions or unavailable native capabilities become agent-callable.
- The auditor accepts an omitted, extra, duplicated or metadata-mutated planner
  entry because it trusts the generated file as its denominator.
- A new canonical query or a changed canonical reference is not projected.
- Registration sends an ordinary Node network request or receives inherited
  provider credentials while generating discovery data.
- Fixing planner discovery changes the existing HTTP catalogue.

The negative auditor controls invoke generation, not just `--check`: a stale
coverage report is not the intended rejection. They require a canonical-planner
diagnostic, rather than passing because an unrelated frontend or filesystem
guard happened to fail.

## Evidence and limits

The runner retains inputs, source hashes, borrowed dependency locations, direct
canonical observations, commands, exit statuses, outputs and case results.
Snapshot workspace dependency links are rebound to the snapshot's own source.
Third-party installed dependencies and the parent Git HEAD are borrowed;
this is not a cold install or independent Git checkout. The earlier sealed
cold-reconstruction proof is separate.

Only synthetic source/manifest mutations occur in the private snapshot.
Ordinary Node HTTP, HTTPS, fetch, TCP, TLS, DNS and datagram entry points are
denied in the independent observation process. This is not an OS sandbox,
child-process network confinement or a proof about all transitive import code.
No database, server, provider, FINNOR action or real business effect is driven.

Run before implementation and again after repair:

`node scripts/centropy/verify-capability-discovery.mjs --evidence-dir /absolute/private/workspace/directory`

Use Node 22 and the two already installed locked dependency graphs. A baseline
failure must be retained; passing source-contract checks do not close the
authenticated native-observation, mounted-product, physical recovery, clean
installed application, comparator, protected-custody or business gates.
