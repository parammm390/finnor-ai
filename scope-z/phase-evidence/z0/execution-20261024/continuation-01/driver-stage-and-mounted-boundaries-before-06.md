## Confirmed failures in the current verifier

1. `CURRENTNESS` accepts a caller-labelled stage and arbitrary snapshot subsets.
   It neither stops the actual worker at that stage nor verifies its live
   delivery fence. A timestamp or unrelated event changes the whole snapshot
   digest. That does not prove a rights/source/terms/code/checker/consumer/parent
   dependency changed.
2. Code/checker/consumer cases have only HTTP fault steps. None of the closed
   existing operations can change the actual local loaded source bytes.
3. The refusal comparison uses the case's initial consumed-event count.
   A dispatch cut can lawfully follow a previously current consumption. The
   comparison must use the actual pre-fault cut, retain its action, and forbid
   forward stale dispatch rather than silently relabel the cut as intake.
4. The useful positive uses HTTP steps for acquisition. `mount()` only opens,
   reloads, reads and screenshots. It does not drive the real learning form,
   its native reservation submission, Refresh current scope, or an actual
   root/principal switch.
5. The browser client stores the real Supabase session in localStorage and adds
   its bearer in the maintained transport. The verifier's independent
   `browserContext.request.get("/api/centropy/me")` sends no such bearer.
   Cookies alone cannot authenticate this proxy. Observe the actual mounted
   `/me` response and its request authorization, then use that same verified
   bearer for independent native reads. Never manufacture an Auth context.
6. A tenant-wide rights revision can invalidate another case's already
   delivered original fixture. Require distinct existing real tenant/owner
   credentials for the four rights cases and a real login when selecting
   that actor. Do not create a tenant, grant or principal to satisfy coverage.
