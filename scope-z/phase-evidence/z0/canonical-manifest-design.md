# Canonical capability convergence: pre-code shape decision

Evidence is coordinator-local source/runtime enumeration, not a dedicated
Z0 launch or authenticated installed owner flow.

The actual Node 22 canonical runtime probe enumerated 77 PE capabilities,
without provider credentials and with parent Node HTTP/fetch/socket calls
denied. It invokes registration/metadata only, no actions. The six lexical
omissions include shared actions, wait/check and the native economic
transition; required Work references also differ.

## Two whole-shape implementations considered

1. Execute the actual canonical registration/manifest function in a bounded
   separate Node process using the existing pinned TS loader. Project its
   complete entries into discovery and independently audit exact canonical
   identities/metadata. Deny ordinary network calls and pass no provider
   credentials during enumeration. No duplicate action list.
2. Extend the lexical generator or introduce an AST/list mirror. This avoids
   module loading but creates a second incomplete interpreter of dynamic
   constructors, unions and future metadata; today's six patched omissions
   would not establish future completeness.

Choose (1), subject to failure-first source-contract E2E and checking both
test and production registration environments without credentials. Keep the
canonical entry's available/health/modelProposable values exactly, including
native economic transition available=false/modelProposable=false. Internal
query metadata does not add public OpenAPI intents or HTTP effect authority.
Wait/check kinds and all required references must survive projection.

Generator/audit compilation cost is not a scored runtime speedup. Native
owner reachability, mounted behavior, physical recovery, clean final install
and full Z0 remain unproved. D1 requires the deeper original-input/native
observation investigation, not a parser-only fix.
