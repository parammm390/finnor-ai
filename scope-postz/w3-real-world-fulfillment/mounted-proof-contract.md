# Mounted owning-boundary proof contract

Specified before the mounted driver and canonical Work-link refinement.

The earlier W3 intake supplied only `activeContext.worldRoot`. Inspection of the canonical `receiveWork` owner shows that it derives attachments from `entityRefs`, `focusedEntity`, `selectedEntities` and explicit `entityAttachments`, not `worldRoot`. Thus W3 must submit the exact original company through that existing attachment port. The fixture must create this original Work/link before fitting the S3 model and deriving its S4/S5 parents; it may not silently refresh a stale parent after adding a new world fact.

Mounted validation uses the emitted committed-source Next installation, the existing same-origin disposable-auth host, actual signed local password authentication and actual production handlers/SQL. No mock API or test-only product route supplies a programme.

Independent predicates:

- The original company projection contains the exact canonical Work and its native attachment. The selected Work mounts the W3 panel and all seven original instance IDs from its authenticated read.
- A rendered continuation control reaches the actual authorized advance route and durable queue, then the production worker. Read-only rendering cannot start procurement.
- A participant sees only that participant's purpose-bound protocols. Another principal/tenant cannot read the owner's W3 Work or private S1 originals.
- A successful real owner response may be held outside the handler, for at most 20 seconds. Logout, principal A→B→A, offline→online, root navigation and authority revocation must not allow that old response to repopulate the private programme.
- An offline transition actually changes browser network state; a page event alone cannot establish offline recovery.
- Returning to the original root/Work requires a fresh successful authenticated read. Reload uses the same emitted bytes and actual restored session. Consent revocation and expiry are distinct from logout and must remain visible as refusal/currentness gaps, not physical success.
- Backend/API restart and a new mounted read retain original Work, request, deadline, parent allocation, failures and unresolved monetary cost.

The original embedded-pane method above is superseded by the coordinator's
29 October instruction: launch a separate, visible headed Chromium with a new
task-owned profile. Do not attach to Factory's pane or any personal/running
browser. Use ordinary rendered controls and real keyboard/pointer input for
login, root selection, Work selection and consent. Never inject credentials or
session state through DOM, storage, cookies or an API. Read-only DOM predicates
remain observations, not input substitutes. No headless fallback is allowed.

Before counting a mounted case, retain the actual browser product/version,
executable digest, Playwright version, fresh-profile identity, visible-page
observation and original-command-line checks for no headless flag and the exact
owned profile. Only the newly launched context may be closed. The disposable
profile lives under `/tmp` and is removed after closing that context; no personal
profile, shared browser process or cache is changed. Browser automation package
bytes must be copied into the installation, not resolved from a donor checkout.
The host's existing Playwright-managed Chromium is an explicitly declared
verification dependency, not an emitted product component or portable-runtime
claim; its actual identity is re-observed separately in the cold run.

No real external contact, genuine human evidence or field qualification is
permitted. Disposable credentials remain in memory/private input, not public
evidence. Screenshots are taken only after login/password controls are gone.

Before the final headed adapter is frozen, cleanup must retain a receipt even
if restoring the disposable principal, closing its owned context or deleting
its profile fails. A failure in one cleanup step must not skip later independent
cleanup steps or stopping the owned frontend host. Preserve the original case
failure together with cleanup failures; never promote an incomplete cleanup to
a passing mounted result. An unconfirmed context close leaves an explicit
task-owned profile follow-up, not a claim that the profile was removed.

Screenshots, bounded DOM predicates, real handler response hashes/barrier transitions and SQL/queue records must be retained. Source/type/build checks alone do not pass this gate.
