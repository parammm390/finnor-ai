# S6 bounded request IR and independent verifier — before implementation

The ordinary compiler may propose a concrete adapter request for an existing
DurableObligation. It cannot activate that request or change the obligation's
immutable semantic identity. Ring-0 mechanically verifies a bounded IR against
an authenticated accepted obligation and externally issued exact-method admission
and current effect-bound authorization. A provider-field mapping is itself an
independently admitted contract; naming PRICE_CHANGE does not imply that changing
any convenient field performs it. No method/admission is invented by the compiler.

Candidate declared transport: conditional single-record JSON field replacement,
explicit HTTPS provider origin/account/resource/version, scalar fields including
null/clear, maximum 64 exact obligation channels and 16 fields per member. No raw
HTTP methods, headers, credentials, redirects, file paths, arbitrary code, predicates
or fallback routes enter IR. Provider units/dose semantics require exact independently
signed mapping evidence. Other methods fail closed. This candidate is not an
admitted or live-provider domain until its production integration and external
admission/protection/staging evidence actually pass.

Threats: producer changes tenant/principal/effect/source/allocation, target/account,
method version/source digest, dose/unit/operation/channel count, precondition/expiry,
null semantics, request hash, refinement or budget. Replay expired/wrong-source S8
signature or producer-generated approval. Empty/vacuous IR and duplicate members,
prototype/oversize/deep JSON, source mutation, unavailable protected audit, or
credential exposure through proposed headers/URLs must be rejected.

Admission/root keys and issuer signatures are separately provisioned. Local test
keys only exercise DISPOSABLE_TEST_AUTHORITY, never production promotion. The verifier
has no planner, optimizer, database engine, economic estimator or generic executor.
It cannot conclude business truth from an owner-signed assertion. Current owner
rechecks, last-egress fences, native attempts, liability and independent observation
must still be integrated through the real protected broker before execution is admitted.

Test authoring gate: (1) actual API compiler preserves exact native obligation and
all channel meaning, then independent process verification rejects altered requests
and unqualified admission; (2) blindly accepting producer targets, producer approval,
or signed but wrong-version admission breaks it; (3) existing owner preparation
stops with UNADMITTED and cannot test concrete request identity; (4) public compiler
and protected verifier endpoints are production integration, no test-only flags.
Use actual S4/S5 owner obligations and independently generated attack inputs. Retain
no-admission results as refusals, not proof of permitted egress or economic value.

First integration step exposes ordinary compile-request through the actual owner API.
Its concrete target/account/field proposal remains unadmitted and cannot dispatch.
The independently released ledger process offers mechanical request verification,
requiring an accepted S6 obligation preimage and externally pinned S8 admission
root. A successful mechanical check still returns executionAuthorityGranted=false:
current owner resolution and actual egress mediation are separate remaining work.
There is no production signer/admission fallback. Source identity for the verifier
is mandatory in both reviewed ledger release and method admission. These explicit
partial qualifications remain part of the full completion gate.

Retained baseline `request-ir-absence` failed with four other owner checks passing,
but the new compile-request case accidentally selected the S5 handler's default.
It is fixture-routing evidence, not evidence about the S6 endpoint. The harness
now explicitly calls the actual S6 handler for positive and negative IR inputs.
Rerun `request-ir-absence-owner` is the prospective capability baseline. No
production IR code was written before this correction.

The exact owner baseline returned S6 NOT_FOUND (four dependency checks passed).
The first compiler declares a single-dose conditional replacement only. It rejects
multi-period channels rather than collapsing their schedule; it preserves the full
intervention, owner references, resources, rights and deadlines in IR. This is a
proposal limitation, not a change to the frozen S6 required provider domain.
The owner runner now records before/after source digests, explicit nonsecret
auth/test configuration and exact process command so artifacts remain reproducible.
This tooling validates source stability; it adds no production authority or seams.

Protected verifier authoring registration: extend the existing separate-process
ledger owner E2E, using an actual S4/S5-produced native obligation from the owner
run and a fresh API compilation. Independently issued S8 test-domain method
admission fixes the precise scalar mapping, account, record, source versions and
validity. It is deliberately not production release, semantic scientific proof,
current owner authority or an egress grant. Observable signature verification is
performed outside the process. Rehash altered IR inputs so semantic attacks reach
the verifier rather than only failing their content hash. Test signed but expired,
wrong-source and mismatched-method admissions, missing/foreign accepted obligation
references, duplicate/partial members and audit corruption. Existing ledger tests
protect immutable append but do not test request semantics. No test-only production
flags; external root and reviewed source set are normal production configuration.
The baseline must reach the absent /verify-request endpoint after authenticating
and registering the actual obligation. Its 404 is missing capability evidence.

`request-verifier-absence` reached the actual endpoint with an accepted native S6
obligation; 13 established ledger contracts passed, and the two new capability
cases failed on missing endpoint. This is a prospective baseline, not a repaired
live exploit. `request-verifier-owner` passed the 15 integration challenges,
including rehashed semantic/request attacks and signed expired/wrong-source
methods. Root/script typechecking found control-flow narrowing errors; they are
retained and repaired without changing checks. The revised run captures full
protected and compiler/owner source identity plus the upstream artifact digest.
