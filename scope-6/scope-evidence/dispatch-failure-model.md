# Protected dispatch and native settlement — preregistration

This closes an owned missing path. It does not qualify a live provider or confer
production admission. The existing obligation owner E2E is the primary test owner;
extend it before its intentional rights revocation, using its genuine current S1,
S3, S4, S5 and canonical effect records. No second action/effect identity is issued.

Authoring gate: (1) observable contract is exact, currently authorized single-dose
conditional mutation through a separate protected process, durable possible-egress
responsibility and independently read target-bound S5 settlement; (2) credible
failures include request substitution, credential access before verification,
stale authority, process death after provider acceptance, redirect/replay, false
readback and early resource release; (3) existing compiler/ledger/transport proofs
never dispatch this obligation or give S5 actual protected settlement; (4) use
real HTTP/TLS, owning APIs, filesystem permissions, SIGKILL and ordinary PostgreSQL
roles. No production fault flag, test-only export or bypass is needed.

Declared initial adapter is CONDITIONAL_JSON_RECORD_V1: exact HTTPS origin and
account, encoded record path, strong If-Match version, one PATCH attempt with
fixed canonical fields and operation identity. Independently provisioned admission
and business-owner authorization are required. A separate GET must return the
same account/record, operation identity, changed strong version and exact own
fields. Wrong record, null, missing field, stale version, conflicting operation,
partial members, unavailable audit and any ambiguous transport retain unresolved
responsibility. No consequential replay after an ATTEMPT, even after restart or
idempotency expiry. A GET does not prove absence or permit another PATCH.

The broker uses the protected ExperienceLedger as its attempt/observation history,
one OS kernel writer lock for dispatch, fixed signed routes and private credentials.
The ordinary native owner authenticates the caller and checks current S1/S4/S5
bindings outside Ring-0; a nonce-bound, short-lived signed assessment is fetched
again immediately before the wire. The final gap is bounded but not atomic with
remote acceptance; later revocation cannot undo an in-flight effect. Production
depends on independently provisioned owner/signing services and an isolated OS
identity; disposable keys remain test authority only. Generated workers have none
of the native database, signer, broker or provider credentials.

Cases in the existing native owner test: authenticated exact compilation and
independent admissions; foreign/signature/request substitution without provider
egress; actual accepted PATCH with lost response then SIGKILL; wrong-record/null
GETs cannot settle; recovery GET establishes the exact prior operation with no
second PATCH; concurrent recovery preserves one consequence; native S5 accepts
only allocation/consumption/effect-bound protected evidence, deduplicates it and
retains the original reservation envelope when actual costs are unknown. Current
rights suspension before dispatch must refuse at the native owner boundary.

Budgets registered before code: 2 MiB input, 1 MiB provider response, 64 members,
256 protected history records per obligation, 32 queued broker requests, one active
dispatch, 5-second owner assessment validity, 10-second individual request,
30-second broker work deadline, 15-second boot, 10-second shutdown, 120-second
case budget excluding existing upstream fixture construction. Exact source/runtime
digests, TLS public identity, local authority scope, requests, independent reads,
PIDs/signals, receipts, native transitions and rerun command are retained. Missing
metering never becomes zero spend; S5 does not release merely because fields match.

Reuse decisions: existing PostgreSQL/tenant owner serialization, canonical effects,
Node HTTPS/crypto, fs-ext kernel lock and ExperienceLedger. RFC 9110 If-Match
preconditions and Node HTTPS certificate validation define the transport boundary;
neither establishes provider compliance. No new workflow engine is introduced.
Primary references: https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match and
https://nodejs.org/api/https.html#httpsrequesturl-options-callback.
