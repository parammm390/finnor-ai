# Independent acceptance specification, revision 1

This record precedes producer, checker and reference implementation. The
checker receives the immutable ORIGINAL owner input and a proposed complete
table, not a producer matrix, row list, utility function or enumeration.
Its Python implementation may use only the standard library. It must not import
the producer, repair LP, TypeScript predicates or native solver bindings.

## Failure model

- A caller forges Work, principal, tenant, source, party/reporting rights,
  current mandate, resources, grant, method, checker or receipt identity.
- A producer omits/duplicates a report, selects multiple/foreign outcomes,
  truncates domains or tests only identities, sampled/truthful opponents.
- A producer evaluates a deviation at the reported rather than true type,
  reverses transfer sign, uses floating tolerance, substitutes zero outside
  options, rounds a boundary or promotes weak ties into consent.
- A producer invents a prior, correlation, discount/FX rule, event probability,
  true-type oracle, future acceptance, settled incoming funds or free subsidy.
- A producer hides a payment date, default liability, cost, escrow, hard
  resource/covenant demand or preexisting/UNKNOWN commitment.
- A producer claims numerical optimality or failed search as a proof, alters
  coefficients, proof basis, domain, original input or checker version.
- An owner reserves one favorable unseen profile, sums mutually exclusive
  profiles, converts nonterminating rational amounts lossily, or creates a
  second reservation ledger.
- A report is relabeled acceptance; one principal submits another party's
  report; a correction after closure changes a fixed mechanism; private values
  survive tenant/Work/session switches or delayed responses.
- Queue retry renews the grant/deadline, forgets a failed child/UNKNOWN attempt,
  duplicates a physical effect, publishes under an expired fence or erases
  agreements/liabilities when scientific applicability is revoked.
- An ordinary receipt, source hash, subprocess exit, owner review or mounted
  display manufactures scientific admission, signer authority or settlement.

## Admitted finite mathematical input

Each party explicitly supplies an identity, reporting principal, rights/source
revisions, distinct finite types, valuation for EVERY type/outcome, and outside
option for EVERY true type/other-report conditioning case. Each scalar is a
canonical arbitrary-precision rational `{numerator,denominator}`. Missing
values are not zero. Numerators/denominators are reduced, denominator positive;
integer and payload growth are bounded with explicit refusal, never truncation.

V1 supports supplied quasilinear utilities, deterministic outcomes, a complete
finite set of contracted dates and unconditional scalar cash components.
Each date has an explicitly supplied utility multiplier, funding, cost and
liability cap. Monetary meaning includes currency, owner, valuation date, time
unit and discount convention. No event-dependent utility, nonlinear preference,
collusive guarantee or unsupported ambiguity receives an unconditional claim.
All schedules remain inspectable when a protected execution method is absent.

Reports are claims. Refusal, decline and no-response are separate no-agreement
events, not extra private types. The table is immutable before reports.

## Acceptance predicate

1. Independently Cartesian-enumerate declared reports. Require exactly one
   table member per vector, one permitted deterministic outcome, every party
   and every declared date exactly once. No private/hidden predicates.
2. Independently compute scalar utility transfers as the supplied sum of exact
   dated cash times the party/type's supplied multiplier. Require all original
   payment, per-date gross-outflow funding, net subsidy/balance, escrow,
   liability, cost, resource and covenant conditions for EVERY profile.
   Future incoming cash never funds earlier outgoing promises. Outstanding
   UNKNOWN commitments retain their full canonical envelope.
3. For each party, true type, arbitrary other reports and nonidentity report,
   evaluate BOTH outcomes at the SAME true type. Require truthful minus
   deviating utility >= 0 at ZERO tolerance. Return the party, true type,
   alternate report, other reports, two utilities, exact gain/margin and
   source/event refs on failure. Four x three x three means 81 profiles,
   648 nonidentity inequalities and 324 ex-post participation comparisons.
4. Compare truthful utility with the exact supplied outside option in EVERY
   conditioning case. Equality is weak participation, not consent.
5. Recalculate the S4 objective using its declared robust/maximin or qualified
   exact joint weights, cost and range. Do not infer a distribution. A bound
   requires an independently reconstructed original-model bound. A general
   numerical solver proof/status is not admitted. UNKNOWN gaps stay UNKNOWN.
6. Reconstruct S4 rule lookup, S5 contingent demand/funding, reservation
   envelope, original quantity meaning and complete S6 proposed schedule.
   Publication/use additionally require current owner/rights/Work/grant/
   method/checker bindings, enforced outside the mathematical child.

## Independent reference and mutations

The small reference enumerates ALL allocation/payment-grid rules for a
registered two-party, two-type, two-outcome domain and checks them directly.
The grid is an explicit reference domain, not a discretization of the general
bounded-rational production problem. Analytical feasibility/infeasibility
witnesses are reconstructed from original values, never solver rows.

Registered full fixtures include an interacting four-party allocation,
nonzero/type-dependent outside options, rational/tied boundaries, liquidity
limits and outcome resource restrictions. The separately registered buyer
posted-price diagnostic is math only. A report-1 rebate must produce exactly
27 profitable true-type-2/report-1 deviations of gain 1.

Mutations target coverage, true-type evaluation, deterministic selection,
outside options, sign/unit/time, hidden predicates, consent, resource/funding,
receipt/code/input/checker bindings and unsupported proof claims. A feasible
candidate with an unproved optimum is accepted only WITH its optimization gap.
