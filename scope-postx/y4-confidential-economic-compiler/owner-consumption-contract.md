# Y4 recipient-owned continuation contract

Recorded before the continuation implementation. This does not relax the frozen
verification population or give a computation source-truth, admission or effects.

- S4 may use an exact released quantity as a recipient-local admissibility guard
  on its existing current policy/decision. It must not relabel the quantity as an
  S2 observation, fitted causal model or measured utility.
- S5 may substitute the exact quantity only into an explicitly marked original
  joint-value term. Currency, entity, consequence period and the original
  accounting/explicit joint-terms reference must match. No resource registry
  balance, policy demand, probability law or original mandate is replaced.
  The actual native optimizer, independent exact checker, reservation and
  consumption owners remain authoritative.
- The release reference is a hiding commitment. Values stay in the recipient's
  existing private S4 store and principal-scoped S5 proposal. Add restrictive
  native SQL policies for confidential derivatives. If another principal cannot
  read a live private reservation, the complete S5 snapshot must refuse, not
  silently omit that reservation or overcommit resources.
- Recheck release/consent/source/Work/method currentness at every owner use and
  under the S5 commit lock. Replays may read original responsibility but cannot
  turn a stale certificate into current clearance.
- S6 prepares the real immutable obligation from the native S4 preparation and
  S5 consumption. It grants no dispatch, provider admission, business signature
  or settlement. Recheck the original preparation in subsequent validation.
  The original analytical Y4 Work is provenance, not execution lineage. Never
  materialize its query PlanNode as an action. Native S6 drafts remain unadmitted
  and have no action Work/PlanNode binding; Y4 records their original analysis
  Work in its existing event owner. Any later dispatch needs its own valid native
  action lineage and all ordinary admission controls.
- S8 consumes a typed commitment-only candidate in the real lifecycle service.
  Its development construction review must bind actual native correspondence,
  runtime and current release evidence. It must not be called an independently
  assigned protected campaign, deployment security approval or financial truth.
  Evaluator and promoter identities and keys remain separate.

Failures to exercise end to end: forged release/term/value/semantics; nonrecipient
owner read; missing or expired consent; revocation before use and during commit;
guard treated as S2 evidence; old or renewed Work/deadline; hidden reservation
omitted from S5; source substitution; S8 self-admission or stale replay; prepared
S6 effect accidentally dispatched; cancellation erasing an existing reservation,
consumption, effect or unknown-outcome history. Preserve every failed attempt.

For the final adversarial continuation, prepare a second actual S5 reservation
and S4 consumption before the first S6 effect exists. Two ordinary, owner-scoped
SQL connections may alternate exclusive locks on that owner's user row. Observe
the real S6 request waiting in its final owner check while holding the native
portfolio mutex, then revoke the other participant's consent through its actual
API before releasing the row lock. This pauses the existing transaction, not a
test hook or rewritten status. Require final refusal and byte-identical S5/S6
responsibility rows across revocation and the failed commit. Bound every wait and
release both test locks on failure.

Revocation itself rechecks original owner authority. Start its real API request
while the final S6 check is paused, observe that revocation already holds the
existing S1 source mutex and waits for the ordinary owner-row barrier, then
release that barrier. Await both requests. This guarantees that revocation
commits before S6 can acquire its source mutex, rather than waiting for a
revocation response while preventing its own authority check.

Run that final-commit race as its own `owner-commit-race` product episode,
immediately after the real owner continuation and before underwriting writes
change S1. The ordinary lifecycle separately proves underwriting, Work completion,
S8, browser and subsequent revocation. Lifecycle 021 reached all those positive
boundaries, but its later pending preparation was refused by current S4 context
before the final barrier. Do not relax that currentness check, revoke and restore
consent, or reuse that episode's native session. The installed-lifecycle gate must
pin both complete, current-driver product reports, including the independently
observed final-commit race and its unchanged native responsibility snapshot.

Give a nonrecipient its own real S3/S4 policy before creating the private effect.
Its actual S4 choice must first work. Afterward, require its SQL effect read to
hide the private row, the complete-context predicate to refuse, and the same
actual S4 choice to fail specifically for outstanding effects, not an invalid
foreign policy reference.
