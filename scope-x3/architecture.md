## Supported profile, frozen before implementation

`PE_FIRM_TYPED_APPLICATION_V1` supports firm-operation record reconciliation,
evidence review, scoped approval and analogous finite-state record workflows.
It does not add portfolio-company operation.

* Owner-authored, independently versioned structured business specifications.
  Free prose without a supported explicit interpretation remains unresolved.
* At most eight entity types, 32 fields per entity, 16 states per entity,
  32 transitions, eight canonical business roles, 64 critical invariants,
  and 128 independently named acceptance conditions.
* Text, boolean, enumerated values, exact quantities, canonical references and
  explicit `UNKNOWN` values with reasons. Exact decimal strings have at most
  38 significant digits and 12 fractional places. Currency, entity, units,
  temporal meaning and accounting basis travel with quantities.
  There is no implicit FX, guessed currency, numeric coercion or missing-to-zero.
* Typed total predicates, finite state transitions, explicit separation of
  duties and canonical evidence currentness. No arbitrary scripts, imports,
  expressions, HTML, SQL, network calls or executable dependencies from input.
* Existing FINNOR Node 22/Next.js API and ordinary PostgreSQL runtime.
  Generated application assets and compiled backend programs are immutable
  release-owned data; installed operations use the actual compiled program.
* At most 1,000 persisted records per application, 16 simultaneous clients,
  eight releases, 16 build attempts and 10,000 business mutations per original
  application allocation. The acceptance run must test declared concurrency.
* Maximum 256 KiB specification, 4 MiB generated release assets, 16 MiB
  application data, 128 KiB request, and 8 MiB response. Bounds refuse rather
  than truncate. Parent deadlines are at most 3,600 seconds and never renew on
  repair, restart or revision. A build has a 30-second computation deadline.
* One build at a time through existing canonical compute capacity policy.
  Bound the typed program and checker work; retain observed CPU, elapsed,
  process-memory, storage and output measurements. Shared-process memory and
  unavailable money/provider/human meters are disclosed, not zeroed.
* Development installations only. Production requires independent S8 admission,
  current deployment/authority and live observations. Development completion
  does not mint protection-domain authority.

These are declared limits, not measured capacity. A failed proof does not
silently lower the profile.

## Computation, failure model and falsifier

The compiler emits a data-only typed backend instruction program and complete
browser assets. The host validates every instruction and never evaluates guest
JavaScript or SQL. Runtime actions consume installed release identity, record
revision, canonical user/role/authority and current evidence before changing
persisted state. All quantities remain exact strings and integer arithmetic.

An independently implemented specification interpreter checks the generated
kernel over a preregistered finite case domain. It does not import the compiler's
decision function. The checker states its exact cases, arithmetic and bounds.
This is bounded kernel verification, not formal verification of the whole app.
Independent application acceptance drives authenticated installed operations,
then inspects actual persistent state.

The principal falsifier is any human application-specific backend/rule/source
repair within a scored construction or maintenance episode while FINNOR reports
autonomous completion. Other critical falsifiers include wrong-role acceptance,
stale revision or authority, quantity reinterpretation, data loss, false
completion/migration, effect replay or completion without independent evidence.

## Installation, lifecycle and recovery

The durable worker builds a candidate, checks it and stages an immutable release.
Installation atomically validates and migrates the complete existing record set,
retains before/after semantic digests and approval history, then changes the
installed head under a current physical job and domain generation fence.
An interrupted build cannot publish through a stale worker. Retry uses the same
parent allocation; it does not replenish resources.

Requirement/rule changes apply explicitly to future decisions on persisted
records. Historical quantities, creation-contract identity and approval events
retain their original meaning. Identity/concurrency and dependency/schema/build
changes use the same impact graph and data-preservation predicate.

Rollback validates every actual record against the destination schema/program
and checks post-release actions and outstanding canonical obligations.
It cannot undo external effects. An unsafe rollback retains state/obligations
and reports an authorized forward repair or exact blocked disposition.
Cancellation fences future construction/actions without erasing accepted data,
costs, effects or observations. No process exit is a restoration receipt.

## Executable development scenario and custody

Independent acceptance is authored before candidate code under
`scope-x3/acceptance/`. The first product reconciles records and requires separate
analyst, partner and compliance activities. Users create competing proposals,
operate under exact quantities/currencies and explicit evidence gaps, refresh
evidence, lose authority, and interact across an interrupted installation.
Later revisions change approval thresholds, add currency, alter identity or
concurrency, and change schema/dependency/runtime identity without clearing data.
A second independently specified application must use a different entity/state
graph, demonstrating synthesis rather than selecting one reconciliation demo.

The local auth fixture verifies real signed bearer tokens and resolves ordinary
canonical users. It is not hosted identity-provider qualification. Disposable
effect authorities remain disposable. No builder credentials enter generated
products. Typed candidate code has no mechanism to read the oracle filesystem.
Development independent authorship is not protected oracle custody.

## Verification and separate gates

Before expensive runs, retain a finite manifest with requirement, owner,
input/source/runtime/schema cut, independent expected result, command, artifact,
status, access, failure family, limits, start/end state and rerun conditions.
New verification uses actual HTTP, queue, physical processes, ordinary SQL roles,
browser actions and installed consumers, not post-code unit tests.

Mandatory affected checks include type/lint, API build, migration bundle/head
and replay/upgrade, generated OpenAPI/client/forms/authorization contracts,
security/history scanning, worker imports/final emitted runtime, fresh/restart/
old-job behavior, installed user/lifecycle and reconstruction parity.
Unavailable Docker/ARM64 final-image proof is a named internal execution blocker,
not inferred from an x86_64 source run.

The matched diagnostic executes equipped X3-enabled and X3-off actors using the
same requirements, data, authority and installed acceptance. No existing missing
operation becomes a zero denominator. Missing equipped construction comparator
or compatible qualified B_V blocks the relevant comparative claim.

Statuses are reported independently: DESIGNED, CODE_COMPLETE, E2E_DEV_VERIFIED,
DOMAIN_QUALIFIED, PRODUCTION_ACTIVE, operational 100x and financial qualification.
Protected admission still requires twenty independently specified applications,
at least 18 complete passes, all critical invariants, sixty withheld lifecycle
episodes with at least 54 passes, independent custody/authority and full costs.
The original common S/P/M/R/V resource, correctness, uncertainty, operational and
financial floors remain unchanged and are not scored using development examples.
