# Unsupported standing rule meaning — pre-code boundary contract

The compiler currently supports explicit event-triggered rules and the declared
ordinary operation inputs. A supplied condition, risk/priority policy or other
unknown normative field cannot be silently ignored while preparing an effect.

Credible regression: add a conditional approval predicate to one independently
retained standing rule without changing its event trigger. The old lowering
still prepares that rule. Required behavior is an explicit unresolved duty with
its original identity/deadline, exact rule and unsupported fields; unaffected
known rules remain eligible. This does not qualify unsupported rule semantics.

Explicit full action/expected-ID/postcondition fields already used by the native
owner cannot be silently overridden by resolved source fields. A disagreement
requires an exact interpretation or correction decision, never a replacement ID.

The existing responsibility driver exercises original→check→lowering and preserves
the expected failing predicate before repair. The actual authenticated source,
mandate, native queue and Work scenario remains NOT RUN.
