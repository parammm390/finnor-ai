## Decided design (implement it, or document precisely why a part cannot be done and what you did instead)
1. Origin execution child, narrow semantics. Add ONE new owner-authenticated request (name it `requestInstitutionApplicationExecution` or equivalent; surface it through the existing authenticated operation route only if a route addition is needed and only after reading the installed Next docs) that creates an execution CHILD session under an institution-origin acquisition parent that is `MODEL_READY`, whose model was accepted by S4 (`S4_INSTITUTION_APPLICATION_MODEL_ACCEPTED`), and whose original P1/responsibility/reservation/deadline are still current (`currentInstitutionApplicationSession`). It continues the ORIGINAL responsibility: same original Work and input (not a fresh Work), the original reservation and deadline (`newAllowance:false`), fresh governed-profile authority through `prepareFreshApplicationAuthority`, target must be allowed by the profile and must NOT be a demonstration target, the child copies the parent's origin reference so `originOf(child)` holds. It does NOT relax `requestApplicationExecution`: that function keeps refusing origin parents (learning is not fresh business authority). The new path must be idempotent (idempotency key + request digest), refuse cross-tenant/other-principal/stale/revoked/cancelled cases, and never create S5 allowance.
2. Viability-governed child. The child must not autonomously run all composition steps. Mark it viability-governed (in its request/parent record, not a free flag a caller can supply). The X2 worker composes (obtains `composition_ref`) and then PARKS (reuse an existing status if the CHECK constraint allows it honestly; otherwise add the status in your migration) until S4 selects a step. A governed child with no selection must be inert (no S5/S6/S8 effect).
3. Retained once-only selection record (new table + forward migration; you OWN exactly one new migration named `postz_z3_s4_executable_selection.sql`, which must sort AFTER the current newest `postz_zi_integrated_source_change_fences.sql`; update `CURRENT_MIGRATION_HEAD` and every place that records the head (grep for `postz_zi_integrated_source_change_fences` excluding `migrations-bundle.ts`), regenerate the bundle with the repo's generator). Unique per (tenant, application session, composition ref, canonical step id, Z3 cursor edge). It stores the Z3 claim identity (job, claim token digest, fence, delivery attempt, session generation), the application session, composition ref, canonical step id, operationId/semanticRevision, original grant, the Z3 cursor/mapDigest and a status machine (SELECTED -> CONSUMING -> RESULT_RETAINED | REFUSED | STALE). RLS and grants consistent with neighbouring Z3/X2 tables (worker role is `finnor_worker`).
4. S4 selection (`selectGeneralExecutableOperationTx` becomes a real writer under its own binding version): in one transaction it re-validates everything it validates now, locks, inserts the selection exactly once (a duplicate delivery of the same Z3 edge returns the same selection, it never creates a second one), and enqueues exactly one `run_application_semantics_v1` job for the child carrying the selection id. The Z3 job then parks with a cursor `pending` selection (UNKNOWN-like) instead of advancing.
5. Application-owner consumption: the X2 worker, with ITS OWN claim, consumes the selection by executing exactly the one selected next canonical step in a step-bounded mode of `continueNativeApplicationComposition` (add an optional bound such as `throughStepId`; default behaviour unchanged for every existing caller). It debits S5 from the ORIGINAL reservation, binds the S6 obligation / stable effect identity before egress, goes through S8, observes independently, and retains a result receipt against the selection. It must not call `publishAssignment` until the goal is established. A lost response or killed worker leaves the S6 identity/UNKNOWN exactly as the existing recovery machinery does; redelivery reconciles, it never replays the wire effect.
6. Z3 reads the retained receipt (like `readGeneralS4ObservationTx`) as the owner result for the E-state and takes the environment edge from the typed result domains; UNKNOWN stays an environment move, never a favourable prediction. Pending UNKNOWN blocks the next selection. Currentness (mandate, source, model, operator, semantics, consent, code/checker, grant) is re-bound at selection, claim, consumption and read; changes invalidate through the existing P7/native invalidation, unrelated work continues.
7. Evidence/versioning: the executable path gets its own binding/evidence/cursor version. Existing v2 review evidence, mapDigests and the Z3 public suites must be byte-for-byte unaffected (run the existing Z3 public/offline checks before and after).
