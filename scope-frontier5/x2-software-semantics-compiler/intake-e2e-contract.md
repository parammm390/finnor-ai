# Corrected intake: failure model and independent oracle (before harness)

This is a narrowly scoped, ordinary disposable registration E2E. It is not a
learner, business-completion, S8, protected-admission or production test.
Preparation alone is **EXECUTED=false**. Run serially only when the parent
schedules it; do not overlap the original-lease cancellation/expiry episode.

- Copy maintained frontend input bytes from that installation to a private

- Real native profile/account rows, disposable credential files and the native

- No worker/queue dispatcher is started. Genuine acquisition registration must

## Registered failures and pass predicates

1. **Fake/local refusal or writes before refusal.** On one mounted maintained
   panel, submit a well-formed UUID absent from canonical auth_profiles. The
   unmodified emitted owner must return actual HTTP 404 with exact code
   `X2_ACQUISITION_PROFILE_UNAVAILABLE`. Browser request and real response are
   retained. Before/after SQL must show unchanged tenant sessions, S5 requests,
   proposals, reservations, reservation origins, consumptions and application
   requests. A stubbed 404, client validation error or generic 404 fails.
2. **Incorrect replay fence after explicit refusal.** Without navigation,
   reload, remount or auth reset, the same panel must display the explicit
   owner-refusal message, empty canonical sessions and enabled acquisition
   inputs/button. Correct its form to the real existing profile with identical
   target/resource/deadline values. Form clearing by the maintained product is
   expected; the driver refills through ordinary visible controls.
3. **Fabricated/optimistic success or wrong scope.** Corrected submission must
   receive real HTTP 202 with a validated UUID, then render exactly that
   QUEUED session. SQL must join the original parent/session, Work owner/input,
   tenant/principal/root, S5 reservation/allocation/consumption and queued job;
   projection must match the same scope. No learned model, business success,
   dispatch, effect or release is inferred.
4. **Duplicate registration.** Exactly two acquisition POSTs for corrected
   intake (one refused, one accepted), exactly one accepted canonical session,
   one original reservation and one unclaimed acquisition job. Refresh and a
   finite 3500 ms observation window must not create another request/session.
5. **Unsafe clearing after ambiguous response loss.** On the separate new
   Work/profile/resource, intercept only that acquisition transport. Deliver
   its genuine request to the real backend using `route.fetch`, verify its
   actual 202 and canonical registration, retain the response privately, then
   abort the response to the page. Never fulfill synthetic 2xx/404. Observe
   actual transport failure and the maintained unconfirmed-outcome notice.
   Post-response real projection may expose the registered session, but the
   unconfirmed replay fence must remain (no acknowledgement UUID reached the
   client). It must survive explicit canonical refresh, with visible native
   fence language and disabled fresh-use form. Exactly one acquisition POST,
   session/reservation/job; no retries during the finite negative window.
6. **False fixture/auth/custody success.** Require browser password sign-in and
   backend SDK user verification observations; preserve installation integrity
   at beginning/end, pin copied frontend source bytes, and verify no dispatch
   or application request/model/effect. Missing assets, disk, startup/auth
   failure, timeouts or cleanup errors fail/block; never relax bounds or report
   partial progress as PASS.
